Data Ingestion and Preprocessing Pipeline
=========================================

The first stage of the ``drive_cycle_calculator`` pipeline is **Data Ingestion and Preprocessing** (Stage 1). This stage takes raw telematics exports (such as Excel or CSV files generated by the Torque OBD-II app) and converts them into standardized, clean, uniform 1 Hz Parquet archive files.

Once ingested, the raw files are never re-read; the Parquet archives serve as the permanent, immutable source of truth for all downstream analysis and synthesis.

---

Preprocessing Pipeline Flow
---------------------------

The preprocessing pipeline follows these steps to transform raw files into canonical archives:

.. mermaid::

   flowchart TD
       raw["Raw Export\n(.xlsx / .csv)"] --> parse["1. Parsing & Separator Sniffing\nWhitespace stripping, numeric coercion"]
       parse --> validate["2. Column Validation & Fallbacks\nStrict curated checks, Fuel flow rate fallback"]
       validate --> QA["3. QA Checks\nDropping speed outliers (>300 km/h), GPS Time gap scanning"]
       QA --> resample["4. 1 Hz Resampling\nUpsampling (interpolation) or Downsampling (mean aggregation)"]
       resample --> meta["5. Metadata Embedding\nUserMetadata, IngestProvenance, ComputedTripStats"]
       meta --> save["6. Archive Parquet (v2)\nzstd compressed, canonical filename stem"]

---

1. Parsing and Separator Sniffing
---------------------------------

To support varied operating system locales and exporter apps, the pipeline handles flexible CSV parsing:

Whitespace Normalization
~~~~~~~~~~~~~~~~~~~~~~~~
Torque exports frequently include leading or trailing spaces in column headers. The constructor strips surrounding whitespace from all column names immediately.

Placeholder Conversion
~~~~~~~~~~~~~~~~~~~~~~
Empty data entries or Torque's dash placeholders (``-``) are parsed and coerced into float64 ``NaN`` (Not a Number) values.

CSV Auto-Detection
~~~~~~~~~~~~~~~~~~
When loading CSVs via ``OBDFile.from_csv()``:
* **Separator Sniffing**: Uses ``csv.Sniffer`` on the first 20 lines to detect the delimiter (e.g. ``,``, ``;``, or ``\t``).
* **Decimal Inference**: Scans the preview lines for comma decimal formatting (e.g. ``\d+,\d+``) to distinguish European separators from standard dot decimals.

---

2. Column Validation and Fallbacks
----------------------------------

The pipeline requires a minimum set of core telematics channels for downstream kinematic and fuel consumption analysis.

Curated Columns
~~~~~~~~~~~~~~~
The validator enforces the presence of the five curated columns (``CURATED_COLS``):
* ``GPS Time`` (consumed to produce ``elapsed_s``)
* ``Speed (OBD)(km/h)``
* ``CO₂ in g/km (Average)(g/km)``
* ``Engine Load(%)``
* ``Fuel flow rate/hour(l/hr)``

In strict mode (always used by the CLI), missing curated columns raise a ``ValueError``.

Fuel Unit Fallback
~~~~~~~~~~~~~~~~~~
If the canonical ``Fuel flow rate/hour(l/hr)`` column is absent, the constructor attempts to synthesize it from alternative columns in order:
1. ``Fuel Rate (direct from ECU)(L/m)`` :math:`\times 60`
2. ``Fuel flow rate/hour(gal/hr)`` :math:`\times 3.78541`

---

3. Data Quality and Outlier Filtering
-------------------------------------

Two quality checks are executed before resampling:

Speed Outliers
~~~~~~~~~~~~~~
OBD sensors sometimes emit extreme speed glitches (such as :math:`3 \times 10^{38}` km/h). The pipeline filters out any speed readings strictly exceeding **300 km/h**.

GPS Time Gaps
~~~~~~~~~~~~~
The system scans consecutive rows in the ``GPS Time`` column. If the time delta between any two consecutive timestamps exceeds ``max_gap_s`` (default 5.0 seconds):
* **Normal mode**: Logs a warning containing the row index and gap duration.
* **Strict mode**: Raises a ``ValueError`` immediately, allowing the CLI to skip the file.

---

4. Uniform 1 Hz Resampling
--------------------------

GPS and OBD logging rates can suffer from time jitter or oversampling. The pipeline normalizes the time grid using a median delta (:math:`\Delta t`) check:

Downsampling (Median :math:`\Delta t < 0.5` seconds)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
If the logging rate is faster than 1 Hz (e.g. 5 Hz oversampling):
* Numeric columns are aggregated to 1-second bins using the **mean** value.
* Non-numeric columns are aggregated using the **first** value in the bin.

Upsampling (Median :math:`\Delta t \ge 0.5` seconds)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
If the logging rate is standard (with jitter) or has missing intervals:
* A uniform 1-second interval ``DatetimeIndex`` is generated.
* Numeric columns are filled using **linear interpolation**.
* Non-numeric columns are filled using **forward-fill** (last observation carried forward).

Duplicate timestamps are removed and sorted chronologically before resampling.

---

5. Metadata and Provenance Embedding
------------------------------------

Each Parquet archive embeds a JSON metadata block under the PyArrow schema key ``dcc_metadata``. This guarantees auditable provenance:

.. list-table:: Embedded Parquet Metadata
   :widths: 25 75
   :header-rows: 1

   * - Namespace
     - Description
   * - ``IngestProvenance``
     - Contains the UTC timestamp of the ingestion run and the original raw source filename.
   * - ``ComputedTripStats``
     - Stores GPS summary statistics calculated from raw coordinates: start/end times and the mean and standard deviation of latitude/longitude.
   * - ``UserMetadata``
     - Flattened metadata filled by the user (driver name, vehicle make, model, engine size, year, fuel type, category).
   * - ``IngestConfig``
     - Record of resampling settings, gap thresholds, and strictness applied during the ingestion run.

---

6. Canonical Filename and Storage
---------------------------------

To prevent key collisions and standardize organization, archive files are named using a canonical stem:

.. math::

   \text{filename} = \text{t}\{\text{YYYYMMDD-hhmmss}\}\text{-}\{\text{duration\_s}\}\text{-}\{\text{hash6}\}\text{.parquet}

* **Time**: UTC timestamp of the first valid GPS row.
* **Duration**: Total elapsed duration of the trip in seconds.
* **Hash6**: The first 6 characters of the SHA-256 hash of the concatenated latitude and longitude coordinate bytes (reverts to a hash of the file stem if GPS coordinates are missing).

The data is saved as a **v2 Parquet archive** (all raw columns preserved, zstd compressed, version 2.6).
