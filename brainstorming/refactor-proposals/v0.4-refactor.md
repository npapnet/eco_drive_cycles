# v0.4 Refactor: MicrotripSegmenter + `trip.microtrips`

## Corrected Problem Statement

The original proposal (`microtrip-refactor.md`) described segmentation logic as living
*inside* `Trip`. This is inaccurate. As of the current codebase the logic is already
extracted to `segmentation.py` as two standalone functions:

- `detect_boundaries(speed, config) → list[SegmentBoundary]` — Stage 1, no `Trip` dependency
- `build_microtrips(trip, boundaries, config) → list[Microtrip]` — Stage 2, the factory

`Trip.segment(config)` (`trip.py:242`) is a 12-line thin entry-point that calls both.
The separation the proposal asks for is already in place at the function level.

**The real gaps are:**

1. **`trip.microtrips` does not work.** The property at `trip.py:230` raises
   `NotImplementedError`. After calling `trip.segment(config)`, the result is returned
   but not stored on the trip — there is no way to retrieve it again without re-running
   segmentation.

2. **No first-class segmenter object.** There is no single object that owns the config
   and drives both pipeline stages. Users either call `trip.segment()` or invoke the
   two low-level functions directly. There is no collection-level segmentation entry
   point.

3. **No collection-level segmentation.** `TripCollection` has no method to segment all
   its trips in one call.

4. **Stale code.** `TripCollection.to_duckdb_catalog()` is present in
   `trip_collection.py:183–259` but `CLAUDE.md` states it was removed (DuckDB is now
   produced by `dcc extract`, not `TripCollection`).

---

## Design Constraint

After segmentation, `trip.microtrips` must return the segmented result. The Trip must
store its own microtrips so they are accessible without re-running the segmenter. This
requires that the segmenter writes into the Trip (a deliberate side-effect — see
trade-offs below).

---

## Proposed Changes

### 1. `Trip` stores segmented microtrips (`trip.py`)

Add two instance fields in `Trip.__init__`:

```python
self._microtrips: list[Microtrip] | None = None
self._segmentation_config: SegmentationConfig | None = None
```

Replace the `NotImplementedError` stub with a real property:

```python
@property
def microtrips(self) -> list[Microtrip]:
    if self._microtrips is None:
        raise RuntimeError(
            f"Trip {self.name!r} has not been segmented. "
            "Call MicrotripSegmenter(config).segment(trip) or trip.segment(config) first."
        )
    return self._microtrips
```

Add a read-only public alias for auditability:

```python
@property
def segmentation_config(self) -> SegmentationConfig | None:
    return self._segmentation_config
```

`trip.segment(config)` becomes a one-line convenience wrapper (backward-compatible):

```python
def segment(self, config: SegmentationConfig) -> list[Microtrip]:
    from drive_cycle_calculator.segmentation import MicrotripSegmenter
    return MicrotripSegmenter(config).segment(self)
```

Calling `trip.segment(config)` a second time with a different config **overwrites**
`_microtrips` and `_segmentation_config`. This is intentional — re-segmenting replaces
the previous result with no ambiguity about which config produced it.

### 2. `MicrotripSegmenter` class (`segmentation.py`)

A configuration-owning object that drives both segmentation stages and populates
`trip._microtrips` in place.

The constructor accepts either a `SegmentationConfig` object or raw keyword arguments
forwarded to `SegmentationConfig`. Users only need to know about `MicrotripSegmenter`
for the common case; the config object is still available at `segmenter.config` for
serialization or reuse.

```python
class MicrotripSegmenter:
    def __init__(
        self,
        config: SegmentationConfig | None = None,
        **kwargs,
    ) -> None:
        self.config = config if config is not None else SegmentationConfig(**kwargs)

    def segment(self, trip: Trip) -> list[Microtrip]:
        """Segment trip into microtrips. Stores results on trip._microtrips."""
        data = trip.data
        if "smooth_speed_kmh" not in data.columns:
            trip._microtrips = []
            trip._segmentation_config = self.config
            return []
        speed = (
            pd.to_numeric(data["smooth_speed_kmh"], errors="coerce")
            .fillna(0.0)
            .reset_index(drop=True)
        )
        boundaries = detect_boundaries(speed, self.config)
        microtrips = build_microtrips(trip, boundaries, self.config)
        trip._microtrips = microtrips
        trip._segmentation_config = self.config
        return microtrips

    def segment_collection(
        self, tc: TripCollection
    ) -> dict[str, list[Microtrip]]:
        """Segment all trips in a TripCollection.

        Returns {trip.name: [Microtrip, ...]}. Each trip in tc is also
        populated in place — tc.trips[i].microtrips works after this call.
        """
        return {trip.name: self.segment(trip) for trip in tc.trips}
```

`detect_boundaries` and `build_microtrips` remain as-is. `MicrotripSegmenter.segment()`
absorbs the logic currently in `Trip.segment()`.

### 3. Remove `TripCollection.to_duckdb_catalog()` (`trip_collection.py`)

Dead code since v0.3. DuckDB is produced by `dcc extract`. The method contradicts
`CLAUDE.md` and has no callers in the current codebase. Removing it eliminates the
inconsistency.

## API Examples

**Single trip — kwargs form (ergonomic for notebooks and quick experiments):**

```python
segmenter = MicrotripSegmenter(stop_threshold_kmh=3.0)
segmenter.segment(trip)

print(trip.microtrips)          # list[Microtrip]
print(trip.segmentation_config) # SegmentationConfig — config that produced the result
```

**Single trip — explicit config object (preferred when config is reused or serialized):**

```python
config = SegmentationConfig(stop_threshold_kmh=3.0)
segmenter = MicrotripSegmenter(config)
segmenter.segment(trip)

print(segmenter.config.model_dump_json())  # serialize for run record
```

**Single trip — convenience shorthand via Trip (backward-compatible):**

```python
trip.segment(config)
print(trip.microtrips)          # list[Microtrip]
```

**Collection:**

```python
segmenter = MicrotripSegmenter(stop_threshold_kmh=3.0)
result = segmenter.segment_collection(tc)     # dict[str, list[Microtrip]]
for trip in tc:
    print(trip.name, len(trip.microtrips))    # each trip is populated in place
```

**Accessing microtrips before segmentation raises clearly:**

```python
trip = Trip(df=df, name="test")
trip.microtrips  # → RuntimeError: "Trip 'test' has not been segmented. ..."
```

## Design Decisions and Trade-offs

### Why a class rather than keeping module-level functions?

`detect_boundaries` and `build_microtrips` as standalone functions are already clean.
`MicrotripSegmenter` adds a small amount of ceremony. The justification:

- **Config ownership**: one object holds the config and applies it consistently across
  all calls — no risk of passing a different `SegmentationConfig` to `detect_boundaries`
  vs. `build_microtrips`.
- **`segment_collection()`**: natural home for the collection-level entry point.
- **Future extensibility**: a different segmentation strategy (e.g. kinematic rather
  than speed-threshold based) can subclass or replace `MicrotripSegmenter` without
  changing `Trip` or `TripCollection`.

The module-level functions stay as-is and remain testable independently.

### Why mutate `Trip` from the segmenter?

The constraint is `trip.microtrips` works after segmentation. The alternatives are:

| Option | Description | Problem |
|--------|-------------|---------|
| **Mutate Trip (chosen)** | Segmenter writes `trip._microtrips` | Side effect, but explicit: documented on the method |
| `SegmentedTrip` wrapper | New type that wraps `Trip + microtrips` | New type, new constructors, breaks `TripCollection` type annotations, significant churn |
| `trip.segment()` writes self | `Trip.segment()` stores result on `self` | Already the pattern — `MicrotripSegmenter.segment()` just moves the logic |

Mutation is the right call here: it avoids a new type, and `Trip._microtrips = None`
is an honest representation of "not yet segmented".

### Why not absorb `SegmentationConfig` fields directly into `MicrotripSegmenter`?

Absorbing config as mutable attributes (`segmenter.set_stop_threshold(3.0)`) would
break three things:

- **Auditability**: `trip.segmentation_config` stores the config that produced the
  microtrips. A mutable segmenter attribute could be changed after the fact, making
  the stored value stale.
- **Serialization**: `SegmentationConfig` is a Pydantic model — JSON-serializable,
  validated at construction, immutable. Segmenter attributes are none of these.
- **Validation timing**: the 5-second floor on `microtrip_min_duration_s` fires at
  `SegmentationConfig()` construction. With setter methods it would have to be
  re-validated at `segment()` call time.

The `**kwargs` constructor resolves the ergonomics friction without merging the two
concerns: users don't need to import `SegmentationConfig` for the common case, but the
config object exists as a proper value object under `segmenter.config`.

### `trip.segment(config)` kept as convenience

Removing it would break the existing test suite and all current callers. It becomes a
one-liner wrapper. No reason to remove it.

### `to_duckdb_catalog` — remove, not deprecate

It was officially removed in v0.3 per `CLAUDE.md`. Keeping it with a deprecation warning
perpetuates the inconsistency. A hard delete is cleaner; there are no external callers.

## Out of Scope → TODOS.md

These are real improvements but outside this refactor:

- **Analysis output folder** (`dcca-<YYYYMMDD-hhmm>/trips`, `/microtrips`): new CLI
  subcommand, likely `dcc segment`. Non-trivial; add to backlog.
- **TripCollection as result type / subsetting**: `TripCollection` is intentionally a
  dumb container — it is the *output* of a subsetting operation, not the entity that
  performs it. Filtering belongs either in constructor parameters
  (`from_archive_parquets(path, user="John")`) or in a standalone utility function
  (`subset_by(tc, user="John") → TripCollection`). Add constructor-level filter params
  to the backlog for when multi-driver datasets make this a real need.
- **Microtrip export to Parquet**: persisting microtrips to disk for offline analysis.
  Downstream of this refactor.
- **`TripCollection.find_representative_microtrip()`**: top P1 item in `TODOS.md`.
  Downstream of this refactor; unblocked once `trip.microtrips` works.
- **`PipelineConfig` root model** combining `ProcessingConfig + SegmentationConfig`
  (mentioned in `microtrip_design_spec.md §3.1` but never implemented). Out of scope
  here; would require changes to CLI and all pipeline entry points.
